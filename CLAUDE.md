# Skittlers league websites

- Hosted on Netlify, connected to this repo: every push to `main` deploys to production.
- Only commit and push when the user asks; a push to `main` goes live.
- Workflow: develop in the session and push to GitHub only when the user says the work is finished. After each change, rebuild the clickable preview (`node dev/build-preview.mjs <scratchpad>/preview.html`) and republish it to the same Artifact so the user can try it in Claude. The preview runs the real `lib/core.mjs` API in the browser. `npm run preview` runs a local server for browser tests; sign up as `owner@skittlers.test` for the overall admin.
- `public/index.html` is the whole front end (`/` = account area, `/<slug>` = a league; later `<slug>.skittlers.co.uk`). `lib/core.mjs` is the API; `netlify/functions/api.mjs` wraps it with Netlify Blobs.
- Data model: accounts (`users/`, `emails/`), leagues (`leagues/`, `slugs/`), and per season `seasons/<league>/<season>` (teams, venues, fixtures, divisions, cups, transfers, committee) plus `contacts/<league>/<season>`.
- Secrets (`SESSION_SECRET`, `SUPERADMIN_EMAIL`) live in Netlify environment variables. Never commit a `.env` file.
- Captains' addresses and mobiles are stored separately ("contacts") and must only be returned to the league's secretary or the overall admin.
- League settings (`leagues/<id>.settings`): points for win/draw/loss, players a side, balls a hand, hands each player throws, the game (rough skittles or nomination), the tie-break order, the usual start time for league games (`startTime`, default 19:45) and the colour scheme (`theme`). Each division and cup can set its own `game`; otherwise it plays the league's.
- Only league secretaries for now; other roles (results secretary, captains) come later. Subscriptions are yearly, set by the overall admin until payments are added.
- Cups (Manage cups page): knockout tournaments, team or individual player, full tournament or straight final. Rounds and byes are worked out from the number of entries; only the draw and results are stored, and later rounds are derived from them.
- Add-ons: the overall admin sets each one (photo reading, match night reports) as included in the basic subscription or an extra given per account (`site/settings` and `users/<id>.photos|.reports`).
- Photo reading: the secretary photographs the board and Claude fills in the scorecard for checking. The overall admin sets `users/<id>.photos {until, monthlyLimit}`; readings are counted in `usage/<league>/<yyyy-mm>`. The API stores a job in `board-jobs/` and `netlify/functions/read-board-background.mjs` reads it with the Claude API (`lib/claude-reader.mjs`; needs `ANTHROPIC_API_KEY`, optional `BOARD_MODEL`/`BOARD_EFFORT`). The preview reads photos through the Claude app instead. `BOARD_FAKE=1 npm run preview` makes up readings for local tests.
- Home page (`#home`, the default public page): division tables side by side, the next match night, news and photos. News posts are stored per league in `news/<league>`; photos in `media-index/<league>` with each image (and a `/thumb` copy) at `media/<league>/<id>`, served as images by `GET /api/public/<slug>/media/<id>`. Admins manage both on the News & photos page; photos linked to a cup also show on that cup's page.
- Publishing results: results, scorecards and notes reach the public only when published. Each fixture keeps a working copy plus `pub` (what was last published), a private `note` with a `notePublic` tick, and a `ready` ("checked") tick; Fixtures & results groups games by night with a Publish now button. Cups work the same way: each cup has `check` (per match id, or `final`: note, notePublic, ready) and `pub` ({ results, final, notes }); Manage cups has Publish now per round and Publish final. The public season endpoint (`publicSeason` in core) serves only what's in `pub`. Fixtures and cups without `pub` predate this and are shown as they are.
- Match night reports: when a recent match night's results are all published (or a cup night's last result is saved), the page works out the night's facts (`nightFacts`) and the API has Claude write a report through the same background function. It is saved as a draft news post for the secretary to check and publish; drafts are never public.
- Calendar feed: `GET /api/public/<slug>/calendar.ics` (optional `?team=`, `?division=`, `?season=`) serves the season's dated league games, cup matches and cup finals as iCalendar from published data only (`seasonCalendar` in core). Cup rounds come from `cupMatches` in core, which must stay in step with `cupBracket` in the page. League fixtures has an Add to calendar button (Google, Apple, copy link).
- Player transfers (Manage teams, players & roles): moving a player records `transfers[id] {date, first, last, nick, key, from, to}` in the season and moves them between teams' player lists. Stats follow a player's games for the old team (up to the transfer date) to the new team via `transferKey`; each game keeps the team they played for. The latest transfer of a player can be undone.
- Results from captains: with a captains' code set in League setup (`leagues/<id>.captainCode`, never public; `takesResults` is), the public Send a result tab lets captains pick the date, their team and fill in the scorecard. `POST /api/public/<slug>/seasons/<sid>/submissions` checks the code and card (`cleanCard`), stores it in `submissions/<league>/<season>` and emails the league owner through Resend when `RESEND_API_KEY` and `MAIL_FROM` are set. Admins see a count on the Fixtures & results tab and approve (fills the fixture, ticked as checked), approve and publish, or reject.
- Committee (Manage teams, players & roles): President, Chairman, Treasurer and Secretary (one each, stored under those ids) and any number of committee members, each a player picked from the season's teams, in the season's `committee`. Shown on the home page under Meet your committee with the team they play for now (`committeeTeam` follows transfers).
- Colour schemes (League setup → Look of your site): `THEMES` in the page (between `THEMES-START`/`THEMES-END`) are a header and highlight colour each; `themeTokens` works out every colour for light and dark mode and shades text until it reaches 4.5 to 1. `dev/themes.test.mjs` (part of `npm test`) checks every scheme's text pairs.
- Help & requests: each account has one conversation with the overall admin in `support/<userId>` (messages, unread counts both ways). Secretaries use the Help & requests page (also linked from the league header); the overall admin replies under Messages. Pages check for new messages every 20 seconds while open and the counts every minute. New messages are emailed to `SUPERADMIN_EMAIL`, replies to the secretary, through Resend when it's set up.
- Sharing news: each published post has its own address `/<slug>/news/<id>` with Share buttons (phone share, Facebook, WhatsApp, X, copy link). `netlify/functions/share.mjs` serves that address as the app with the post's preview tags (`newsSharePage` in core: title, opening text, first photo); the page then opens the post at `#news/<id>`. Asset paths in the page are absolute (`/vendor/...`) so they load from that deeper address.
- Downloads: admins add files on the Downloads admin page (PDF, Word, Excel, CSV, text, JPEG, PNG; up to 4 MB, 60 per league; the first bytes are checked against the kind). Index in `docs-index/<league>`, each file at `docs/<league>/<id>`; served by `GET /api/public/<slug>/docs/<id>` (PDFs and pictures open in the browser, `?download=1` or any other kind downloads). The public Downloads tab shows once there's a file.
